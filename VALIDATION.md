# Version 0.2 validation

Checked on 20 October 2026.

- **Python: 46 tests passed.** Includes account registration/login, hashed passwords/tokens, persisted sessions, absolute expiry, single/all-session revocation, administrator password recovery, closed registration, rate limits, bounded bodies and sanitized secret-validation errors. Two users cannot read, refresh or delete each other's trips. Identical flight lookups use independent credentials and caches. Usage/history, concurrent spending, request limits and budget exhaustion are independent per account. Keys are encrypted and owner-bound; no key-read route exists; invalid keys are not saved; replacement/removal preserves spending and permanent key ownership. Missing keys never fall back to a global key or another user's key. Missing/wrong master keys and nonempty legacy shared databases fail closed. Existing billing, month-boundary, timeout, caching, retention, local-date matching and aircraft-reassignment checks pass. New cases cover whitespace/case normalization before length validation, normalized duplicate detection and route derivation without airport input.
- **Native build succeeded.** SwiftUI application, iOS 17 deployment target, no third-party app packages. Simulator session checks use local ad-hoc signing and a temporary DerivedData directory so Keychain access works without an Apple development certificate.
- **Connection-first startup passed.** Four targeted native UI cases pass across the onboarding and final-navigation runs. Fresh/signed-out launches show the connection page without main tabs or demo flights. Demo entry is explicit, and demo Settings can return to the connection page. The two-leg demo add/restart flow accepts spaced flight numbers without airport fields and saves canonical labels.
- **Native account flow passed.** From the dedicated start page against the localhost mock-provider fixture: discover server, register, finish API-key setup before entering the main tabs, view usage, add `lh 2055` without airport input, verify the displayed `LH2055` and derived HAM–MUC route, terminate/reopen while signed in, sign out to the start page, register another user with an empty journal, then sign back into the first account without re-entering its provider key. Saved flights return only for their account.
- **Native usage check passed.** A mocked paid flight lookup appears as one paid lookup with $0.01 reserved, $0.025 provider-reported spend and a $0.035 conservative total. Fractional cents remain visible; monthly history matches the account. The Usage tab shows remaining budget, the last provider check and pricing review date.
- **Existing native trip flows passed.** Connected-flight creation/restart, journal/detail/settings and one/two/three/four-flight overview checks passed during this update. The overview retains its per-leg incoming-aircraft cards.
- **Actual Swift client integration passed.** Discovery, register/login, write-only key setup, two connected flights entered with spaces and no airports, derived route/aircraft decoding, independent account usage/history, empty second-user journal, deletion and session revocation were exercised against the Python HTTP fixture. Swift encoding checks cover case, regular spaces, tabs, newlines and nonbreaking spaces, and ensure airport fields are absent from new requests. Trip status aggregation checks also pass.
- **Visual review completed.** The new start page and simplified single/connected-flight forms, account login, API-key guide, connected-account Settings, fractional-cent usage breakdown and monthly history were inspected in the native simulator. Saved screenshots in `previews/` use fake accounts and provider data. The final build was installed on the original FlightDeck Review simulator without uninstalling it; its saved account and trip reopened successfully. The live localhost server was restarted against the same database and encryption key.

All automated provider checks use deterministic HTTP mocks and fake credentials. The onboarding checks run on a separate simulator from the user's real-key test, preserving that device's session and account storage. Windows service installation, the real HTTPS endpoint/certificate and physical-device installation still require deployment verification. The updated Windows installer and account/key backup instructions are prepared. Push remains deferred.

The server suite emits the existing Starlette TestClient deprecation warning; all assertions pass. This is development validation, not an independent security audit. This version replaces the shared-token prototype; see `server/SECURITY.md` before upgrading any existing live database.

## Advance schedule correction

The original recent-flight-only implementation left a flight three days ahead unresolved and lost the lookup explanation on automatic refresh. The connector now buys filtered advance schedules and verified airport metadata through the same conservative account budget.

- Seven additional server tests cover route/timezone derivation, exact endpoint reservations, daily caching, forced refresh with metadata reuse, schedule-to-live transition while the daily snapshot is fresh, insufficient-budget blocking before a paid request, ambiguous schedules, errors surviving state reads, throttled refresh and server restart, and automatic recovery after a one-minute rate limit.
- The native schedule UI test passes against the mock fixture. It verifies ZRH–HAM, the canonical LX1052 label, explicit Schedule only status, the incoming-aircraft explanation and planned aircraft type without claiming On time. Swift trip-state checks cover mixed live/schedule journeys.
- Real-provider verification succeeded on the original simulator: the user’s existing LX1052 for 23 October resolved to ZRH–HAM, 08:30–10:00 local, with schedule-only labeling. Account/session, encryption key and the complete usage ledger were preserved. This check used the user’s already-configured key through the authenticated app, without reading or exporting it.
- Prices were checked against FlightAware’s official pricing page and OpenAPI 4.30.0 on 20 October. Schedule and airport requests reserve twice their published prices; the operational ceiling remains $4.50.

- Foundation/Swift checks pass for SWISS/Lufthansa-style titles, normalization, title false-positive rejection, duplicate events, skipped cancelled/all-day/completed events, timezone-local departure dates, exact 12-hour and overlapping-flight boundaries, eight-leg grouping, stable import IDs, and exclusion of calendar titles from server payloads.

Physical-device permission prompts and real Google Calendar sync will be checked after server deployment, as requested. No real calendar was accessed, and this feature’s automated tests did not make paid provider requests.

## Reverse-proxy URL support

- Foundation checks pass for root and prefixed servers, explicit ports, trailing slashes, nested prefixes, scheme-less HTTPS addresses, IPv6 and preserved refresh query parameters. Unsafe dot segments, encoded path escapes, embedded credentials, fragments, invalid ports and remote plaintext HTTP are rejected.
- The actual Swift client passes discovery, registration/login, write-only key setup, connected-flight creation, usage/history, user isolation, deletion and session revocation against the mock fixture at both its root and `/flights/` URLs. All authenticated calls keep the configured prefix.
- The native account UI test passes through `/flights/` (124.75 seconds), including registration, key setup, usage, adding a flight, restarting with the saved session, signing out, an isolated second account and signing back in. The saved server address retains the prefix across these transitions.
- A signed ARM64 iPhone build succeeds using the installed personal development identity and passes strict code-signature verification. Physical-device installation still requires a provisioning profile that includes the target phone.
- The production Python routes remain rooted at `/v1/`. A reverse proxy must strip `/flights` before forwarding, preserve query strings and authorization, and avoid redirects. HTTPS and system certificate validation remain required for remote servers.
