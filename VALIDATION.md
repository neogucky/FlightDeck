# Version 0.2 validation

Checked on 20 October 2026.

- **Python: 26 tests passed.** Includes account registration/login, hashed passwords/tokens, persisted sessions, absolute expiry, single/all-session revocation, administrator password recovery, closed registration, rate limits, bounded bodies and sanitized secret-validation errors. Two users cannot read, refresh or delete each other's trips. Identical flight lookups use independent credentials and caches. Usage/history, concurrent spending, request limits and budget exhaustion are independent per account. Keys are encrypted and owner-bound; no key-read route exists; invalid keys are not saved; replacement/removal preserves spending and permanent key ownership. Missing keys never fall back to a global key or another user's key. Missing/wrong master keys and nonempty legacy shared databases fail closed. Existing billing, month-boundary, timeout, caching, retention, local-date matching and aircraft-reassignment checks pass.
- **Native build succeeded.** SwiftUI application, iOS 17 deployment target, no third-party app packages. Simulator session checks use local ad-hoc signing and a temporary DerivedData directory so Keychain access works without an Apple development certificate.
- **Native account flow passed.** Against the localhost mock-provider fixture: discover server, register, verify/store a test API key, view usage, add a live-fixture flight, terminate/reopen while signed in, sign out, register another user with an empty journal, then sign back into the first account without re-entering its provider key. Saved flights return only for their account.
- **Native usage check passed.** A mocked paid flight lookup appears as one paid lookup with $0.01 reserved, $0.025 provider-reported spend and a $0.035 conservative total. Fractional cents remain visible; monthly history matches the account. The Usage tab shows remaining budget, the last provider check and pricing review date.
- **Existing native trip flows passed.** Connected-flight creation/restart, journal/detail/settings and one/two/three/four-flight overview checks passed during this update. The overview retains its per-leg incoming-aircraft cards.
- **Actual Swift client integration passed.** Discovery, register/login, write-only key setup, flight/snapshot decoding, independent account usage/history, empty second-user journal, deletion and session revocation were exercised against the Python HTTP fixture. Trip status aggregation checks also pass.
- **Visual review completed.** Account login, API-key guide, connected-account Settings, fractional-cent usage breakdown and monthly history inspected in the native simulator. Saved screenshots in `previews/` use fake accounts and provider data.

No real FlightAware API key was supplied, and no paid provider calls were made. All live-provider behavior in these checks uses deterministic HTTP mocks. Windows service installation, the real HTTPS endpoint/certificate and physical-device signing still require deployment verification. The updated Windows installer and account/key backup instructions are prepared; no Windows server or Apple account resources were changed. Push remains deferred.

The server suite emits the existing Starlette TestClient deprecation warning; all assertions pass. This is development validation, not an independent security audit. This version replaces the shared-token prototype; see `server/SECURITY.md` before upgrading any existing live database.
